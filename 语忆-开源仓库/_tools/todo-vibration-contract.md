## 1. 数据模型（`index.html` 内 `state.todos`）

```js
{
  id:      "t4",                  // 唯一 id
  text:    "周三前把课题初稿发到群里",
  done:    false,
  from:    "语音新增" | "手动新增" | "来自 AI 总结：…",
  at:      1759603200000,         // epoch ms；null = 无提醒时间
  mode:    "vibrate" | "ring",    // 提醒方式；at 为 null 时无意义
  reminded: false,                // 是否已提醒过（已提醒=已标记）
  snooze:  0,                     // 延后次数
  firedAt: null                   // 实际触发时刻 epoch ms（用于「原定提醒时间」播报）
}
```

**展示串（唯一算法，`remindLabel(t)`）**

| 条件 | 输出 |
|---|---|
| `!t.at` | `无提醒` |
| `t.mode === "vibrate"` | `震动提醒 · 10月8日 09:00`（今天则 `今天 20:00`，明天则 `明天 09:00`） |
| `t.mode === "ring"` | `铃声提醒 · 今天 20:00` |

**列表条目无障碍朗读串（`todoAria(t)`）**：`震动提醒模式，待办内容<text>` / `铃声提醒模式，待办内容<text>` / `无提醒，待办内容<text>`

> 修订说明（Lead，v1.1）：规范 §5.1 原文要求振动标识朗读为「震动提醒模式」，故取值改为 `震动提醒模式`（同时含子串「震动提醒」与「待办内容」，两种写法都成立）。

## 2. 振动节奏（安卓专属三段式，硬性数字）

```
单组 = [200, 100, 600, 150, 200]   // 短震200 停100 长震600 停150 短震200
共 3 组，组间间隔 2000ms
```

**时长口径（Lead 裁定，v1.1）**：规范原文「总时长约18秒」与它自己给出的节拍数字**不自洽**——
按字面节拍算：单组 200+100+600+150+200 = 1250ms，3 组 + 2 次组间隔 = 1250×3 + 2000×2 = **7750ms ≈ 7.75s**，不是 18s。
裁定：**节拍数字优先**（它们是精确值），`约18秒` 解释为**整条提醒的生命周期窗口**（振动窗口 7.75s + TTS 慢速重复 2 遍，合计约 18s）。
因此断言口径为：
- 振动节拍：单组 `[200,100,600,150,200]`、共 3 组、组间 `2000ms`（硬性）
- 提醒窗口：`≈18000ms`（软性，`REMIND_WINDOW_MS = 18000`）
- TTS 第一遍在**第一组振动结束后**启动（延迟 = 单组时长 1250ms）

- 停止条件：说「知道了 / 明白了 / 停」、「点击通知」、「打开待办页面」→ 立即 `navigator.vibrate(0)` 并清定时器。
- 降级：`!("vibrate" in navigator)` → 自动切铃声提醒模式，播报「当前浏览器不支持震动，已切换为声音提醒」。
- 静音/勿扰：振动照常请求，不受影响（浏览器层不读取静音状态，不得伪造"已静音"判断）。

## 3. 提醒触发顺序（分层）

1. **振动**（立即）→ 2. **系统通知**（同刻，常驻：`requireInteraction:true`，`tag` 用待办 id，不自动消失）→ 3. **语音播报**（第一组振动结束后启动，`待办提醒：XXX`，慢速重复 2 遍）。

- 多条同时触发：按 `at` 升序**逐条串行**，上一条处理完再触发下一条（振动+语音不叠加）。
- 后台挂起导致延迟：触发时播报带原定时间「待办提醒：XXX，原定提醒时间XX点XX分」，不静默修正。
- 后台播报：浏览器退到后台用通知通道兜底（通知 body 带全文），页面隐藏时 TTS 仍尝试播报。

## 5. 语音指令（加入 `ROUTES`，与现有 chip 体系打通）

| 指令（任一命中） | ROUTES key | 行为 |
|---|---|---|
| 待办事项提醒 / 新建待办 / 提醒我 | `todoStart` | 进入 5 步录入流程（内容→确认→时间→方式→最终确认） |
| 知道了 / 明白了 / 停 | `todoAck` | 停止振动与播报、标记已提醒、关通知、回待机 |
| 延后十分钟 / 等会儿再提醒 | `todoSnooze` | 停止当前提醒，10 分钟后按同规则重新触发 |

chip 新增两个（在业务指令组）：`data-cmd="todoAck"`「知道了」、`data-cmd="todoSnooze"`「延后十分钟」。
现有 `data-cmd="todo"`「提醒我……」保留，改为进入 `todoStart` 流程。

**录入 5 步播报话术（逐字使用）**

1. `请口述录入待办事项内容，说完后说完成录入。`
2. `已识别待办事项：XXX，请问内容是否正确？`
3. `请问设置提醒时间？` → 成功：`提醒时间：明天下午三点，对吗？`；失败：`抱歉，我没有听清时间，请说清楚几点几分`；连续 2 次失败：`您可以说几月几日几点几分。`
4. `提醒方式选择闹钟响铃，还是震动？` → 震动后补 `震动提醒将通过手机马达振动提示，请保持页面在浏览器中运行。`
5. `待办事项：XXX；提醒时间：XXX；提醒方式：震动提醒，请问确认保存吗？` → 成功：`待办事项保存成功，到点将震动提醒。`

## 6. 后台保活（四层）

| 层 | 规则 |
|---|---|
| 时间校准 | `visibilitychange`、屏幕点亮、`online/offline` 变化时全量重算所有 `at` 的剩余毫秒并重排定时器 |
| 锁屏校验 | 页面隐藏时每 60s 轻量校验，误差 > 30s 自动修正 |
| 心跳 | 隐藏状态下每 90s 一次极小计算心跳（仅更新时间戳，不耗流量） |
| 唤醒锁 | 触发前 30s `navigator.wakeLock.request('screen')`；提醒结束后立即 `release()`；不支持则静默跳过 |

## 7. 异常处理（对照规范第六章，必须逐条可验证）

| 场景 | 行为 | 播报 |
|---|---|---|
| 不支持振动 API | 降级铃声，不阻塞保存 | `当前浏览器不支持震动，已切换为声音提醒` |
| 通知权限被拒 | 保留待办，仅前台触发振动+播报 | `未获得通知权限，后台可能无法收到提醒，建议在设置中开启` |
| 页面被清理 | 下次打开汇总过期待办逐条播报 | `您有X条已过期的待办提醒，分别是…` |
| 后台挂起延迟 | 播报带原定时间 | `待办提醒：XXX，原定提醒时间XX点XX分` |
| 多条同时 | 按时间先后逐条、不叠加 | 依次单条播报 |
| 静音/勿扰 | 振动正常，语音静音 | 无额外提示 |
| 麦克风权限不足 | 不影响提醒 | `麦克风权限不足，无法语音录入待办，提醒功能正常可用` |

## 8. 无障碍（TalkBack / WCAG 2.2 AA）

- 所有新增控件：`aria-label` 明确中文描述，触控目标 ≥48dp（CSS `min-height:48px`）。
- 振动标识 TalkBack 朗读为「震动提醒模式」，列表条目整体朗读 `todoAria()`。
- 提醒弹窗打开即 `focus()` 到标题/首个按钮，焦点圈定，关闭后焦点归还；双指滑动可切换选项。
- 语音指令优先级高于触摸：`ROUTES` 命中立即响应，不等播报读完。
- 纯听觉闭环：录入→确认→提醒→操作全程无需看屏幕。

## 10. 不许做的事

1. 不得删除现有 `openConfirm()` 通用二次确认机制——待办的完成/删除/新建保存继续走它。
2. 不得改动与待办无关的既有功能（录音、原音频、AI 总结、目录、导出记录、帮助）。
3. 不得引入任何外部依赖 / CDN / 网络请求——单文件、离线可用。
4. 不得伪造安卓系统能力（如谎称"已读取系统静音状态"）；规范第七章边界说明必须保留在 UI 文案里。
